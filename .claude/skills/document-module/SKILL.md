# 레거시 모듈 문서화

- 분석 대상 폴더(`$ARGUMENTS` 의 모듈 경로)의 파일은 읽기만 한다. 수정 · 생성 · 삭제하지 않는다.
- 쓰는 파일은 `docs/<모듈명>/` 아래 세 문서뿐이다.
- 모든 설명에 근거 `파일:줄번호` 를 붙인다. 근거를 댈 수 없으면 "확인 필요"라고 적는다.
- 주석과 코드가 다르면 코드를 기준으로 쓰고, 다르다는 사실을 따로 적는다.

## 0. 대상 정하기

- 첫 인자는 모듈 경로, 둘째 인자(선택)는 범위 제한(파일 · 기능 이름)이다. 범위가 있으면 그 안만 분석하고 문서 머리에 범위를 적는다.
- `<모듈명>` 은 폴더 이름이 아니라 아래 셋 중 하나로 바꾼다. 목록에 없는 경로면 멈추고 묻는다.
  - `legacy/item-bank-php` → `item-bank`
  - `legacy/assignment-thymeleaf` → `assignment`
  - `legacy/grade-mssql` → `grade`

## 1. 계획 먼저 제시

- 파일 목록을 뽑고, 읽을 파일 · 단계별 산출물 · 범위 밖으로 둘 것을 짧게 제시한 뒤 진행한다.

## 2. 진입점 → `ARCHITECTURE.md`

- 요청을 받는 지점(PHP 페이지, Controller 매핑, 저장 프로시저)을 표로 정리한다: 경로 · 메서드 · 파일:줄번호 · 역할.
- 저장한 뒤 다음 단계로 넘어간다.

## 3. 의존 관계 → `ARCHITECTURE.md` 에 추가

- 진입점에서 실제로 호출하는 함수 · 클래스 · include 를 코드에서 따라가 호출 방향을 적는다. 외부 의존(DB 연결, 뷰, 다른 모듈)은 따로 모은다.
- 저장한 뒤 다음 단계로 넘어간다.

## 4. 데이터 흐름 → `ERD.md`

- 모듈이 읽고 쓰는 테이블 · 뷰 · 컬럼을 SQL 근거와 함께 정리하고, 스키마(`db/mariadb/init/`, `db/mssql/init/`)의 정의 줄번호를 붙인다.
- 관계는 Mermaid `erDiagram` 으로 그리고, 요청 → SQL → 응답 흐름을 진입점별로 적는다.
- 저장한 뒤 다음 단계로 넘어간다.

## 5. 비즈니스 규칙 후보 → `BUSINESS-RULES.md`

규칙마다 아래 형식을 그대로 쓴다.

~~~markdown
### BR-01
- 규칙: (한 문장. 조건과 결과를 함께)
- 근거: `파일:줄번호`, `파일:줄번호`
- 근거 코드:
  ```
  (근거 줄을 그대로 인용. 고쳐 쓰지 않는다)
  ```
- 확신도: 확실 | 추정   (확실 = 조건문 · SQL 로 확인, 추정 = 이름 · 주석으로 짐작)
- 비고: (주석과 다름, 다른 곳의 중복 구현, 확인 필요 사항)
~~~

- 근거가 주석뿐인 내용은 규칙으로 올리지 않고 "주석에만 있는 내용" 절에 모은다.
- 문서 끝에 "주석과 코드가 다름" 표와 "확인 필요" 목록을 둔다.

## 6. 사람이 표본 점검할 규칙 3개 추천

- 3개를 골라 답변에 ID · 고른 이유 · 확인 방법(열어 볼 줄, 재현 요청)을 적는다.
- 반드시 **가장 그럴듯한 규칙**(확실해 보이지만 틀리면 이관에 영향이 큰 규칙)을 1개 포함한다. 나머지는 추정 규칙, 주석과 코드가 다른 규칙에서 고른다.

## 하지 말 것

- 존재하지 않는 함수 · 파일 · 컬럼을 근거로 쓰지 않는다. 인용한 이름은 Grep 으로 정의 줄을 찾은 뒤에만 쓴다.
- 호출 방향을 추측으로 그리지 않는다. A → B 는 A 의 호출 줄을 근거로 댈 수 있을 때만 적는다.
- 코드에 없는 규칙을 만들지 않는다. 일반적인 관행("수정 시에도 검증할 것")이나 주석 · 함수 이름만으로 규칙을 채우지 않는다. 기능이 없으면 "이 모듈에 없음"이라고 적는다.
- 줄번호는 인용 코드를 쓰기 직전에 파일을 다시 열어 확인한다. 기억으로 적지 않는다.
- 분석 대상 폴더의 파일을 고치거나 새로 만들지 않는다.
